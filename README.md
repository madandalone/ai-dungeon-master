# AI Dungeon Master

Веб-приложение для текстовой настольной RPG по правилам D&D 5e, где роль ведущего играет LLM. Игроки создают персонажей, ведущий заранее придумывает скрытый сюжет кампании и ведёт героев по нему, реагируя на их действия. Исход рискованных действий решает бросок d20, который выполняет игровой движок, а не модель.

![Игровой интерфейс AI Dungeon Master](docs/gameplay.png)

*Экран игры: выбранный герой, летопись приключения и форма отправки следующего действия.*

## Возможности

- Игровые сессии, которые хранятся в SQLite и переживают перезапуск сервера; список и удаление сессий через API.
- Создание персонажей с шестью характеристиками D&D, здоровьем и стартовым предметом.
- **Скрытый сюжет кампании.** Ведущий пишет его по героям при первом ходе новой игры (или по запросу), хранит на сервере и использует во всех следующих ходах. Игрокам он не показывается.
- **Ходы на естественном языке** по-русски. Ведущий либо сразу описывает исход, либо просит проверку характеристики; бросок d20 выполняет только игровой движок, ведущий получает готовый результат.
- **Правила D&D из книги правил.** Rules Service находит нужные разделы SRD 5.1 (поиск по словам, семантический или гибридный) и передаёт их ведущему; русские реплики находят английские правила через словарь терминов.
- Движок единственный изменяет состояние: здоровье, инвентарь, локацию. Ответ модели считается недоверенным и проходит проверку.
- Безопасные повторы и параллельные игроки: повтор хода с тем же `action_id` не применяется дважды, устаревшее состояние клиента отклоняется (`STALE_REVISION`).

## Архитектура

![Схема архитектуры](docs/schema.png)

```text
Browser (Frontend: HTML/CSS/JS)
        |  HTTP, JSON
        v
Backend (FastAPI): сессии, состояние, история, SQLite, идемпотентность
        |
        v
integration/ (TurnOrchestrator, begin_campaign, фабрика, протокол хода)
   |                |                    |
   v                v                    v
Rules Service    AI Dungeon Master    Game Engine
(rules_service/) (ai_dm/, LLM по API) (engine/, чистый Python)
```

| Компонент | Каталог | Ответственность | Документация |
|---|---|---|---|
| Frontend | `frontend/` | интерфейс, отображение состояния, повторы запросов | [docs/implementation.md](docs/implementation.md) |
| Backend | `backend/` | HTTP API, хранение, сессии, кампания, идемпотентность | [docs/backend_application.md](docs/backend_application.md) |
| Оркестрация | `integration/` | связывает компоненты: правила, ведущий, движок; сбои, логи | [docs/turn_orchestration.md](docs/turn_orchestration.md) |
| Rules Service | `rules_service/` | поиск правил в книге, русский словарь терминов, оценка качества | [docs/rules_service.md](docs/rules_service.md) |
| AI Dungeon Master | `ai_dm/` | запросы к LLM, промпты, проверка ответов, память | [ai_dm/README.md](ai_dm/README.md) |

Зависимости направлены внутрь: `integration/` знает про `engine`, `ai_dm.models` и `rules_service`, а они о нём не знают. Контракты между частями описаны в [docs/integration.md](docs/integration.md).

### Игровой ход

1. Игрок отправляет действие (`POST /sessions/{id}/turns`) с `action_id` и `expected_revision`.
2. Если у сессии ещё нет кампании, ведущий пишет её по текущим героям и сохраняет сюжет.
3. Оркестратор проверяет действие и ревизию, находит правила и вызывает ведущего.
4. Ведущий либо описывает исход, либо просит проверку: тогда Backend отвечает `202 awaiting_roll`, а игрок бросает кубик (`POST .../roll`). Цепочка проверок ограничена тремя; первый провал завершает её.
5. Движок проверяет и атомарно применяет последствия, ход сохраняется в SQLite вместе с ответом для повторов.

Сбой поиска правил не останавливает игру (ход идёт без правил, в ответе `warnings`). Сбой ведущего завершает ход ошибкой без изменения состояния.

## Быстрый старт

Нужны Python 3.12+ (разработка велась на 3.13; тесты также проходят на 3.11) и, для ходов с настоящей моделью, ключ OpenAI-совместимого провайдера. Node.js нужен только для тестов интерфейса.

```bash
python -m venv .venv
source .venv/bin/activate          # Windows: .venv\Scripts\activate
python -m pip install -r requirements.txt
cp .env.example .env
```

1. **Книга правил.** Положите markdown-версию SRD 5.1 в `data/srd.md` (каталог `data/` не попадает в Git). Рабочий источник: файл `D&D 5E SRD v5.1 Compilation.md` из репозитория [ucffool/OGL-SRD5](https://github.com/ucffool/OGL-SRD5), его нужно переименовать в `data/srd.md`. Допустимы также `.txt` и `.pdf`.
2. **Настройки.** Отредактируйте `.env` (таблица ниже). Минимум: `OPENAI_API_KEY` и `RULES_BOOK_PATH`.
3. **Запуск.** Одной командой (запускает Backend и статический сервер Frontend, нужен bash):

   ```bash
   ./run.sh
   ```

   или вручную в двух терминалах:

   ```bash
   uvicorn backend.main:app --port 8000
   python -m http.server 5500 --directory frontend
   ```

4. Откройте <http://127.0.0.1:5500>. Документация API: <http://127.0.0.1:8000/docs>.

Адреса `127.0.0.1:5500` и `localhost:5500` разрешены в CORS Backend; для другого порта Frontend нужно изменить список в `backend/main.py`.

### Настройки `.env`

`.env` не попадает в Git; не публикуйте ключи. Шаблон: [.env.example](.env.example).

| Переменная | Назначение | По умолчанию |
|---|---|---|
| `OPENAI_API_KEY` | ключ OpenAI-совместимого API | обязателен для ходов с моделью |
| `OPENAI_BASE_URL` | адрес API | `https://router.huggingface.co/v1` |
| `MODEL_NAME` | идентификатор модели (должна поддерживать JSON Schema) | `Qwen/Qwen3.8-27B` |
| `AI_DM_TIMEOUT_SECONDS` | таймаут запроса к модели | `60` |
| `AI_DM_MAX_RETRY_WAIT_SECONDS` | максимальное ожидание повтора при лимитах провайдера | `10` |
| `AI_DM_LOCAL_WARMUP` | фоновый прогрев модели при локальном Ollama (`0` отключает) | `1` |
| `OLLAMA_KEEP_ALIVE` | сколько Ollama держит прогретую модель в памяти | `15m` |
| `OLLAMA_WARMUP_TIMEOUT_SECONDS` | таймаут фонового прогрева Ollama | `180` |
| `AI_DM_LOG_RAW` | `1` пишет в лог полные промпты и сырые ответы модели (только для локальной отладки: в них скрытый сюжет) | выключено |
| `RULES_BOOK_PATH` | путь к книге правил | обязателен для настоящих ходов |
| `RULES_MODE` | `keyword`, `rag` или `hybrid` | `keyword` |
| `RULES_LEXICON` | `0` отключает русско-английский словарь терминов | включён |
| `RULES_CACHE_DIR` | кэш векторов (режимы `rag`, `hybrid`) | `.rules_index` |
| `RULES_EMBEDDING_MODEL` | модель эмбеддингов | `paraphrase-multilingual-MiniLM-L12-v2` |
| `GAME_DB_PATH` | файл SQLite | `data/game_sessions.db` |

Режим `keyword` не скачивает моделей и подходит для разработки. Режимы `rag` и `hybrid` при первом запуске скачивают модель эмбеддингов (около 470 МБ) и строят индекс книги; если модель недоступна, ошибка конфигурации проявится на первом ходе (оркестратор строится лениво).

Если `OPENAI_BASE_URL` указывает на локальный Ollama на порту `11434`, `run.sh`
прогревает `MODEL_NAME` в фоне. Интерфейс и Backend запускаются сразу; неудачный прогрев
не останавливает проект, но первый ход может выполняться дольше.

## Как играть

1. Откройте игровой интерфейс в браузере.
2. Перейдите в раздел **«Сессия»** через боковое меню.
3. Создайте новую игровую сессию, указав название приключения.
4. В разделе **«Герои»** добавьте хотя бы одного персонажа. Новая сессия создаётся с пустым отрядом.
5. Перейдите в раздел **«Игра»** и выберите действующего персонажа.
6. Опишите действие, например: `Захожу в таверну и спрашиваю трактирщика о пропавших путешественниках`.
7. При первом действии ведущий создаст сюжет по героям, если скрытый сюжет не был передан при создании сессии. Кампанию также можно запросить заранее через `POST /sessions/{id}/campaign`.
8. Для рискованного действия появится карточка с характеристикой, DC, шансом успеха и кнопкой **«Бросить d20»**.
9. После броска дождитесь фиксации кубика. Итоговая формула, повествование и изменения состояния появятся после ответа Мастера.
10. Если связь оборвалась, действие или бросок можно безопасно отправить повторно: результат не изменится и ход не применится дважды.

Разделы интерфейса: **Игра** (действия и летопись), **Герои** (характеристики, здоровье, инвентарь), **Мир** (локация), **Сессия** (создание и переключение).

## API

Backend отдаёт JSON. Ошибки ведущего приходят как `502` с безопасным текстом (без запросов и сюжета).

| Метод | Путь | Назначение |
|---|---|---|
| `GET` | `/health` | проверка доступности |
| `POST` | `/sessions` | создать сессию: `name`, необязательный `hidden_plot` |
| `GET` | `/sessions` | список сохранённых сессий (`id`, `name`) |
| `DELETE` | `/sessions/{session_id}` | удалить сессию и все её данные |
| `GET` | `/sessions/{session_id}/state` | публичное состояние: герои, локация, летопись, ожидающая проверка |
| `POST` | `/sessions/{session_id}/characters` | создать героя: `expected_revision`, `name`, `concept`, `max_hp`, `stats` (шесть характеристик 1-20), `starting_item` |
| `POST` | `/sessions/{session_id}/campaign` | дать сессии сюжет: ведущий пишет его по героям (необязательные `theme`, `monster`) либо принимается готовый `authored` (`title`, `hidden_plot`, `starting_location`, `room_context`, `intro_narrative`); нужен хотя бы один герой (`409 NO_CHARACTERS`); повтор возвращает `created: false`; `409 CAMPAIGN_UNAVAILABLE`, если ведущий не умеет писать кампании и `authored` не передан |
| `POST` | `/sessions/{session_id}/turns` | ход: `character_id`, `text`, необязательные `action_id`, `expected_revision`; `200` исход или `202 awaiting_roll` |
| `POST` | `/sessions/{session_id}/turns/{action_id}/roll` | бросить d20 ожидающей проверки: тело `{"sequence": 1}` (номер проверки в цепочке, 1-3); повтор безопасен |
| `POST` | `/sessions/{session_id}/turns/{action_id}/cancel` | отменить проверку до первого броска |
| `POST` | `/sessions/{session_id}/actions` | техническое изменение здоровья без модели (`character_id`, `text`, `health_delta`) |

Коды конфликтов: `NO_CHARACTERS`, `CAMPAIGN_UNAVAILABLE`, `STALE_REVISION` (клиент отстал от сервера), `PENDING_CHECK` (сначала завершите проверку), `ACTION_ID_REUSED`, `ROLL_ALREADY_STARTED`.

## Демо-кампания «Сундук в сторожке»

Минимальная кампания для показа одного настоящего броска: один герой, одна комната, нет врагов и ловушек. Готовый материал и пошаговый сценарий: [docs/demo_campaign.md](docs/demo_campaign.md), данные: [docs/demo_campaign.json](docs/demo_campaign.json). Сюжет передаётся как `authored`, поэтому модель не пишет кампанию и контекст остаётся маленьким.

## Тесты

Из корня репозитория:

```bash
python -m unittest discover -s engine/tests -p 'test_*.py' -v
python -m unittest discover -s ai_dm/tests -p 'test_*.py' -v        # нужен пакет openai из requirements.txt
python -m unittest discover -s backend/tests -p 'test_*.py' -v
python -m unittest discover -s integration/tests -p 'test_*.py' -v
python -m unittest discover -s rules_service/tests -p 'test_*.py' -v
npm run test:frontend                                               # нужен Node.js
```

Состояние на момент написания: движок 24, AI DM 180, backend 76, интеграция 90 (один тест пропущен без ключа), Rules Service 62, интерфейс 40 тестов, все проходят. Проверки качества поиска правил и часть тестов Rules Service используют полную книгу `data/srd.md` и пропускаются без неё.

Тесты используют заглушку вместо модели, поэтому не требуют ключа и сети. Тесты, опирающиеся на настоящую книгу правил, пропускаются, если нет `data/srd.md`.

### Сквозной сценарий (`integration/tests/test_e2e.py`)

Один тест проходит всю игру через настоящие FastAPI, SQLite, Rules Service, оркестратор и движок: сессия, герой, первый ход с автоматической кампанией, правила на русскую реплику, запрос проверки, d20, повествование, сохранение, перезапуск сервера, повтор хода из базы и продолжение с тем же сюжетом. Подменена только модель. Ещё три теста проверяют сбой правил, вопрос без подходящих правил и управление сессиями.

**С настоящей моделью.** Тот же сценарий запускается против живого провайдера (тратит квоту):

```bash
E2E_REAL_LLM=1 python -m unittest integration.tests.test_e2e.RealLlmScenario -v
```

Нужны `OPENAI_API_KEY` в окружении и доступная модель. Тест проверяет инварианты (ход принят, повествование непустое, сюжет сохранён и не раскрыт, состояние переживает перезапуск), а не слова модели, и печатает краткий итог. Для записи результата сохраните вывод в файл.

### Качество поиска правил

```bash
python -m rules_service.evaluation --book data/srd.md --mode keyword
python -m rules_service.evaluation --book data/srd.md --mode keyword --cases rules_service/gold_queries_ru_holdout.json
```

Метрики и выводы: [docs/rules_service.md](docs/rules_service.md), раздел «Качество поиска» (на независимом наборе из 30 русских запросов правильный раздел входит в пятёрку для 63%, без словаря для 0%).

## Ограничения

- **Настоящая модель.** Успешный ход с живым провайдером в репозитории не зафиксирован: проверки идут на заглушке модели, а у провайдера по умолчанию нужна оплаченная квота (запрос к Hugging Face Router уже возвращал `402`). Сценарий для живой проверки готов (см. выше).
- **Интерфейс и сессии.** Frontend хранит выбранные сессии в браузере (`sessionStorage`) и не вызывает `GET /sessions` и `DELETE /sessions/{id}`; список и удаление доступны через API.
- **Вступление кампании.** При автоматическом старте вступление появляется в летописи после перезагрузки сессии; явный `POST .../campaign` возвращает его сразу.
- **Правила.** Русский словарь знает ограниченный набор терминов (на независимых запросах находит правильный раздел примерно в двух третях случаев); семантический поиск (`rag`, `hybrid`) требует скачивания модели и в репозитории на настоящей модели не измерен.
- **Один процесс.** SQLite и блокировки в памяти рассчитаны на один процесс сервера; идентификаторы повторов хранятся и в базе, но распределённое развёртывание не проверялось.
- **Без авторизации.** Нет учётных записей и синхронизации между браузерами в реальном времени.
- **Качество текста.** Скрытый сюжет и заметки ведущего не попадают в ответы API, но то, что модель не раскроет тайну в повествовании, гарантируют только инструкции, а не код.
- **Старые сессии.** Сессии, созданные до введения шести характеристик, лучше не использовать для проверок навыков.
