# Rules Service

Пакет `rules_service/` даёт Dungeon Master текст правил, относящихся к действию игрока.
Есть три реализации с одинаковым интерфейсом:

| Реализация | Класс | Как ищет | Зависимости |
|---|---|---|---|
| v1: ключевые слова | `RulesService` | BM25 по точным словам | stdlib |
| v2: RAG | `RagRulesService` | косинусное сходство эмбеддингов | `numpy`, `sentence-transformers` |
| v3: гибрид | `HybridRulesService` | RRF-ранжирование объединяет v1 и v2 | `numpy`, `sentence-transformers` |

## Интерфейс (общий)

```python
from rules_service import HybridRulesService, RagRulesService, RulesService
from rules_service.embedder import SentenceTransformerEmbedder

keyword = RulesService.from_file("data/srd.md")
rag = RagRulesService.from_file("data/srd.md", SentenceTransformerEmbedder(), cache_dir=".rules_index")
hybrid = HybridRulesService(keyword, rag)

# или одной функцией по имени режима (так строят и фабрика integration, и проверка качества):
from rules_service.build import build_rules_service
service = build_rules_service("data/srd.md", mode="hybrid", cache_dir=".rules_index")

hybrid.get_rules("Я хочу перепрыгнуть через пропасть", top_k=3, max_chars=4000)  # -> str
hybrid.search("1d6 bludgeoning damage", top_k=3)                                 # -> list[RuleChunk]
```

- Вход: книга правил (`.md`, `.txt`, `.pdf` - для PDF нужен `pypdf`) и текстовый запрос
  (обычно текст действия игрока).
- Выход: `get_rules` - строка `## Заголовок\nтекст` для лучших фрагментов (пустая, если ничего не найдено);
  `search` - список `RuleChunk(title, text, path)`, где `path` - цепочка заголовков (`Movement > Jumping`).
- Обе реализации подходят под `integration.RulesProvider` (`get_rules(query) -> str`), поэтому
  `TurnOrchestrator` и AI DM при замене v1 на v2 не меняются (есть тест).
- Rules Service не знает про движок, DM и Backend.

## Общая часть: разбиение книги

`split_into_chunks(text, max_chars)` режет markdown по заголовкам `#`..`######`, ведёт стек заголовков
(поле `path`), секции длиннее `max_chars` режет по абзацам, а слишком длинный абзац (например, таблицу)
- по строкам. v1 использует `max_chars=1500`, v2 - `500`: многоязычная модель обрезает вход примерно на
128 токенах, более длинный фрагмент был бы эмбеддингом только своего начала.

## v1: ключевые слова

BM25: для каждого слова запроса оценка равна `idf * tf * (k1 + 1) / (tf + k1 * (1 - b + b * len / avg_len))`,
сумма по словам. Две идеи: повторы одного слова дают всё меньше (насыщение, `k1 = 1.5`), а длинные
фрагменты штрафуются относительно средней длины (`b = 0.75`). Параметры стандартные, под набор не подбирались.
Заголовок фрагмента учитывается дважды, токены короче 3 символов отбрасываются. Ограничения: нужно точное
совпадение слов ("leap" не найдёт "jump") и совпадение языка запроса и книги.

Раньше здесь был TF-IDF (`tf / длина * idf`). Он переоценивал короткие фрагменты и фрагменты с одним
многократно повторённым словом; замена на BM25 измерена на размеченном наборе (см. "Качество поиска").

## v2: RAG

```text
книга -> chunks (500 симв., с путём заголовков) -> эмбеддинги -> numpy-матрица (N x 384) [+ кэш .npy]
запрос -> эмбеддинг -> матрица @ вектор запроса (косинус, т.к. векторы нормированы) -> top-k
```

- **Модель**: `paraphrase-multilingual-MiniLM-L12-v2` (sentence-transformers, 384 измерения, работает
  локально). Она отображает тексты на разных языках в общее пространство, поэтому русское действие
  находит английское правило. Модель подменяется через интерфейс `Embedder` (`name`, `encode(texts)`).
- **Текст для эмбеддинга**: `путь заголовков + текст`, чтобы фрагмент "Jump" знал, что он про движение.
- **Хранилище**: обычная numpy-матрица в памяти. SRD 5.1 даёт порядка нескольких тысяч фрагментов
  по 384 числа - это единицы мегабайт, полный перебор по матрице выполняется за миллисекунды.
  Векторная БД (FAISS, Chroma) здесь не нужна; она становится осмысленной при росте на порядки
  (много книг) или при необходимости фильтров/обновления на лету. Интерфейс не изменится.
- **Кэш**: `cache_dir` хранит матрицу в `<хеш>.npy`; ключ - версия формата, имя модели, `max_chars` и
  хеш текста книги, поэтому смена любого из них пересчитывает индекс. Папка `.rules_index/` в `.gitignore`.
  Книга SRD лежит в `data/` (тоже в `.gitignore`) и в репозиторий не коммитится.
- **`min_score`**: нижний порог сходства. По умолчанию 0 (всегда возвращаются top-k). Значение для
  реальной модели нужно подбирать по данным; пока он нужен, чтобы при нерелевантном запросе DM не
  получал случайные правила.

## v3: гибридный поиск (keyword + RAG)

`HybridRulesService(keyword, rag)` объединяет оба подхода через RRF (Reciprocal Rank Fusion):
для каждого фрагмента суммируются `1 / (k + rank)` из обоих ранжировщиков, результат сортируется
по итоговой сумме. `k=60` по умолчанию; при больших `k` разница между близкими рангами
сглаживается, при меньших - резко штрафуются низкие позиции.

Зачем нужен: RAG хорошо ищет по смыслу и на другом языке, но плохо по редким точным терминам
(«1d6», название заклинания, индекс монстра). Keyword наоборот: находит точные слова, но не понимает
перефраз и языков. Гибрид не требует обучения весов и работает сразу.

```python
from rules_service import HybridRulesService, RagRulesService, RulesService
from rules_service.embedder import SentenceTransformerEmbedder

keyword = RulesService.from_file("data/srd.md")
rag = RagRulesService.from_file("data/srd.md", SentenceTransformerEmbedder(), cache_dir=".rules_index")
hybrid = HybridRulesService(keyword, rag)
```

## Контракт сбоев

`rules_service.RulesUnavailableError` означает "источник правил сейчас не может ответить" (не загрузилась
модель эмбеддингов, нет пакета, неполный кэш модели). Это единственный тип, который потребитель
(`TurnOrchestrator`) трактует как "играем без правил". Любое другое исключение - баг и пробрасывается.

- `SentenceTransformerEmbedder` переводит сбой загрузки модели в `RulesUnavailableError` (исходное
  исключение в `__cause__`). Это единственный широкий `except` в пакете, и он оправдан: загрузчики бросают
  несвязанные типы (`OSError` без сети, `ImportError` без пакета, `AttributeError` из `transformers` при
  неполном кэше). Неудачная загрузка не запоминается: следующий запрос пробует снова. Загрузчик модели
  подменяется параметром `loader`, поэтому тесты не импортируют torch.
- `HybridRulesService` при `RulesUnavailableError` от семантической части возвращает результаты
  keyword-поиска и пишет `WARNING`; остальные ошибки не перехватываются.
- `RagRulesService` сам не маскирует сбой: исключение доходит до вызывающего.
- `integration.build_orchestrator` прогревает модель при старте и при её отсутствии завершается
  `IntegrationConfigError`: поломку лучше увидеть при запуске, а не на первом ходе игрока.

## Что проверено автоматически

`python -m unittest discover -s rules_service/tests -t .` - 42 теста:
- v1: разбиение, ранжирование, пустой результат, лимиты `get_rules`; BM25: совпадение нескольких слов
  запроса важнее повтора одного, длинный фрагмент с одним упоминанием проигрывает сфокусированному,
  слово из каждого фрагмента не ломает оценку, пустая книга, параметры меняются;
- v2: русский запрос находит английский фрагмент там, где v1 возвращает пусто; ранжирование по смыслу;
  `min_score`; лимиты; пустой запрос и пустая книга; кэш (не пересчитывается, инвалидируется при смене книги);
- v3: гибрид находит и точные термины (`1d6`), и русские парафразы (`перепрыгнуть`);
- чанкинг: путь заголовков, ограничение длины для огромного абзаца;
- оценка качества: ранг и метрики на подставном поисковике, границы совпадения разделов, формат отчёта,
  корректность набора (все метки существуют в настоящей книге, если она есть);
- сбои: любой сбой загрузки модели становится `RulesUnavailableError`, гибрид деградирует до keyword,
  а настоящие баги не маскируются.

Тесты используют тестовый эмбеддер `ConceptEmbedder` (слова одного смысла - одно измерение): он проверяет
логику поиска, кэша, интеграции и RRF, а не качество реальной модели. Тест `integration/tests` показывает
подмену v1 на v2 внутри `TurnOrchestrator`.

## Качество поиска

Тесты на фейковом эмбеддере проверяют контракт, но не отвечают на вопрос "находит ли поиск правильное
правило". Для этого есть проверка на настоящей книге: `rules_service/evaluation.py` и размеченный набор
`rules_service/gold_queries.json`.

**Набор**: 44 запроса, для каждого указан раздел SRD, в котором лежит ответ (путь заголовков вида
`The Environment > Falling`; все метки проверяются тестом по настоящей книге).

| Группа | n | Что проверяет |
|---|---|---|
| `ru` | 24 | реплики игрока на русском: основной сценарий проекта (SRD английский) |
| `en` | 12 | вопросы на английском другими словами, чем в тексте книги |
| `term` | 8 | точные термины и названия разделов |

**Метрики** (результат считается найденным, если фрагмент лежит в нужном разделе, его предке или потомке):
Recall@k - доля запросов, у которых нужный раздел попал в первые k результатов; MRR - среднее `1/ранг`
первого верного результата (1.0 - всегда первым, 0 - никогда).

**Запуск** (книга лежит в `data/srd.md`, не в репозитории):

```bash
python -m rules_service.evaluation --book data/srd.md --mode keyword
python -m rules_service.evaluation --book data/srd.md --mode rag      # нужна модель эмбеддингов
python -m rules_service.evaluation --book data/srd.md --mode hybrid
```

**Результат для `keyword` (SRD 5.1, фрагменты по 1500 символов, метрики до k=5):**

| Группа | n | R@1 | R@3 | R@5 | MRR |
|---|---|---|---|---|---|
| все | 44 | 0.34 | 0.36 | 0.43 | 0.36 |
| `en` | 12 | 0.83 | 0.92 | 1.00 | 0.88 |
| `ru` | 24 | 0.00 | 0.00 | 0.00 | 0.00 |
| `term` | 8 | 0.62 | 0.62 | 0.88 | 0.68 |

Что из этого следует:
- Русские запросы не находятся вовсе (0 из 24): нет общих слов с английской книгой. Это и есть причина
  существования семантического поиска, а не предположение.
- Английские запросы теперь находятся почти всегда первыми (R@1 0.83, в пятёрке 12 из 12), точные
  термины - в пятёрке 7 из 8.
- DM получает несколько фрагментов (`top_k=3`), поэтому важнее R@3, чем R@1. На всём наборе он 0.36, и
  почти весь недобор - русские запросы.

**Что дало переход с TF-IDF на BM25.** До замены оценка была такой же формулой с `tf / длина` и давала
`en` R@1 0.50 и MRR 0.61, `term` R@1 0.38 и MRR 0.53. Сравнивались четыре варианта (одна и та же книга и
набор, фрагменты по 1500 символов):

| Вариант | `en` R@1 | `en` MRR | `term` R@1 | `term` R@5 | `term` MRR |
|---|---|---|---|---|---|
| TF-IDF (было) | 0.50 | 0.61 | 0.38 | 0.88 | 0.53 |
| TF-IDF + стоп-слова | 0.50 | 0.66 | 0.38 | 0.88 | 0.52 |
| **BM25** (выбран) | **0.83** | **0.88** | **0.62** | **0.88** | **0.68** |
| BM25 + стоп-слова | 0.75 | 0.85 | 0.62 | 1.00 | 0.70 |

Стоп-слова добавлены не были: поверх BM25 они дают разнонаправленный результат (`en` R@1 падает, `term` R@5
растёт), то есть разницу в один запрос из 8-12, а IDF в BM25 и так занижает частые слова. Фрагменты по 500
символов для keyword хуже (`term` R@5 0.75 против 0.88), поэтому для него оставлены 1500.

**Цена выбора.** Точные термины стали лучше в целом, но не все: "death saving throws" 5 -> 1,
"opportunity attacks" 2 -> 1, "critical hits" 4 -> 1, зато "poisoned condition" 1 -> 6 (вперёд выходят
заклинания, где слово "poisoned" повторяется много раз) и "1d6 bludgeoning damage per 10 feet" 4 -> 5.

Набор небольшой (44 запроса, из них 8 и 12 в группах `term` и `en`), поэтому разница в один запрос -
шум. Набор использовался для выбора между четырьмя вариантами выше, но не для подбора чисел внутри них
(`k1` и `b` стандартные). Для проверки уже выбранного решения набор нужно дополнять новыми запросами, а не
подгонять поиск под него.

## Известные ограничения

- Порог `min_score` и параметр `k` RRF нужно выбирать по метрикам из раздела "Качество поиска", а не
  на глаз; набор небольшой (44 запроса), поэтому разница в одно-два попадания - это шум.
- RRF без обучения весов не гарантирует, что keyword всегда победит RAG для точных терминов; для
  критичных случаев можно добавить пост-фильтр по exact match или регулируемые веса.
- Модель скачивается при первом запуске (около 470 МБ) и требует сети один раз.
- Индекс строится синхронно при старте сервиса (на CPU для SRD это минуты, дальше берётся из кэша).
- Нет обновления индекса на лету: при смене книги пересчитывается всё.
