# AI Dungeon Master

Модуль предлагает сюжет и последствия хода. Изменения состояния применяет Game Engine
через существующий TurnOrchestrator.

## Интерфейс

Существующие вызовы сохраняются:

~~~python
from ai_dm.dm_engine import generate_campaign_start, process_turn
~~~

Для тестов и явной сборки приложения доступен AIDungeonMaster(client=None).
Он имеет те же методы generate_campaign_start(request) и process_turn(request).
Экземпляр можно передать в TurnOrchestrator(dm=..., rules=...).
В TurnRequest добавлены необязательные история и acting_character; существующие запросы
без них продолжают работать. Формат TurnResponse не изменён.

## Промпты и проверки ответов

Тексты инструкций хранятся в ai_dm/prompts/ в UTF-8:

| Файл | Назначение |
| --- | --- |
| system.txt | Общие инструкции мастеру |
| campaign.txt | Генерация начала кампании |
| turn.txt | Правила, скрытый сюжет, история, состояние и действие игрока |
| request.txt | Объединение промпта с JSON-схемой ответа |
| repair.txt | Запрос исправления с описанием ошибок проверки |

PromptTemplates в ai_dm/prompts/__init__.py загружает файлы относительно собственного
расположения, а не текущей рабочей папки. Импорт модуля не читает шаблоны. Каждый вызов
generate_campaign_start или process_turn загружает один набор текстов; отбор истории
и повторные запросы используют этот же набор. Изменённые шаблоны подхватываются при
следующей операции. При переносе модуля нужно сохранять каталог prompts вместе с файлами.

В шаблонах используется синтаксис string.Template: `${player_action}`, `${history}`
и другие именованные подстановки. Литеральный знак доллара в шаблоне записывается как `$$`.
Данные игрока, правил, состояния и ответы модели подставляются один раз: содержащиеся
в них фигурные скобки и знаки доллара остаются обычным текстом. Это правило подстановки,
а не гарантия защиты LLM от инструкций внутри входных данных.
JSON-схема по-прежнему строится из Pydantic-модели, а не копируется вручную в файл.
Бюджет контекста считает окончательные сообщения после загрузки и подстановки всех текстов.
Ошибка чтения или заполнения шаблона вызывает ConfigurationError.

Проверки ответов вынесены в ai_dm/validation.py: validate_campaign и validate_turn
получают ответ модели и исходный запрос явно. Они возвращают копию ответа с нормализованным
текстом, проверяют язык и ссылки на персонажей, не меняя входные данные. Игровые правила и применение изменений
остаются за Engine. dm_engine.py управляет вызовами LLM, бюджетом, повторами, разбором JSON
и запуском этих проверок. Публичные модели запросов и ответов сохраняются.

## История ходов

TurnRequest.history — список TurnHistoryEntry с полями:

- character_id — идентификатор персонажа в Engine, по умолчанию пустая строка;
- player_action — действие игрока;
- narrative — повествование принятого хода;
- dm_notes — приватные заметки мастера, по умолчанию пустая строка.

В промпт записи попадают без character_id (memory.history_record): это внутренний
идентификатор Engine, который DM не может сопоставить с именем, а место в бюджете он занимает.
В самом запросе и в хранилище Backend поле сохраняется.

Список передаётся от ранних ходов к поздним. ai_dm/memory.py формирует два блока:

- До десяти последних записей для непрерывности разговора.
- До трёх подходящих более старых записей в блоке «Ранее произошедшие события».

Поиск сопоставляет слова действия игрока и текущей локации со словами из player_action,
narrative и приватных dm_notes старых записей. Упомянутые в действии имена и предметы
учитываются как обычные слова; весь инвентарь автоматически в поисковый запрос не добавляется.
Регистр и различие е/ё игнорируются только при поиске, тексты передаются без изменений.
Числа, слова короче трёх букв и служебные слова из списка в memory.py не учитываются.
Словоформы и синонимы не объединяются: «ключом» может не найти «ключ».

Совпадения с действием имеют приоритет над совпадениями только с локацией. Внутри
каждой группы суммируются веса совпавших слов: чем реже слово среди подходящих старых
записей, тем выше его вес. Повторение одного слова внутри записи не повышает оценку.
При равных оценках выбираются более поздние записи. Точные дубликаты по всем трём
полям не извлекаются повторно и не дублируют последние десять записей.
Отобранные события показываются в хронологическом порядке; history_position — позиция
в переданном списке с единицы, не номер хода Engine. Промпт явно предупреждает о пропусках.

Оба блока входят в общий бюджет сообщений. Сначала исключаются найденные события
с меньшим приоритетом, затем целые старейшие записи из блока последних ходов.
Если последний ход слишком велик, оба блока будут пустыми. Более короткие события
не подставляются вместо более приоритетных ради заполнения бюджета. Исходная история
не обрезается, записи передаются вместе с действием, повествованием и заметками.
Поиск выполняется локально по всей переданной истории, без эмбеддингов, новых зависимостей,
дополнительных вызовов LLM или генерации сводки. Он не гарантирует нахождения всех значимых событий.
Текущее состояние из Engine имеет приоритет над описаниями в истории.
Промпт запрещает раскрывать заметки и скрытый сюжет в narrative, но это инструкция
модели, а не программная гарантия отсутствия утечки в сгенерированном тексте.

AIDungeonMaster не хранит историю между вызовами. Вызывающая сторона отвечает
за выбор истории нужной сессии и сохранение только принятых ходов. Текущий Backend
сохраняет состояние и приватную историю в SQLite и передаёт её через TurnOrchestrator.
Для поиска давних событий нужно передавать полную доступную историю: события,
которые вызывающая сторона уже исключила, восстановить нельзя.
Ошибка LLM или отказ Engine историю не пополняют.

Текущий TurnOrchestrator принимает историю через необязательный аргумент history.
В демонстрации ai_dm.main также сохранён HistoryAdapter: он получает снимок истории,
создаёт копию TurnRequest с этой историей и делегирует вызов DM. Переданная адаптеру история
заменяет history входного запроса, а не объединяется с ней.

~~~python
from ai_dm.dm_engine import AIDungeonMaster
from ai_dm.main import HistoryAdapter
from ai_dm.models import TurnHistoryEntry
from integration import TurnOrchestrator

# state, action, hidden_plot, rules, dice и history предоставляет вызывающая сторона.
dm = AIDungeonMaster()
orchestrator = TurnOrchestrator(dm=HistoryAdapter(dm, history), rules=rules)
outcome = orchestrator.play_turn(state, action, hidden_plot, dice)
if outcome.accepted:
    state = outcome.state
    history.append(TurnHistoryEntry(
        player_action=action.text,
        narrative=outcome.narration,
        dm_notes=outcome.dm_notes or "",
    ))
# Для следующего хода создайте адаптер с новым снимком истории.
~~~

Заметки доступны DM и хранилищу Backend, но не должны входить в публичный ответ
Frontend. Обычный вызов оркестратора без адаптера продолжает работать без памяти.
Адресация персонажей по имени и требование уникальности имён сохраняются.
DM получает явный список допустимых имён для state_updates[].character_name.
После проверки JSON каждое имя сверяется с active_characters текущего запроса:
сокращения, иной регистр и лишние пробелы не принимаются. Неизвестное имя запускает
ту же единственную попытку исправления, что и ошибки формата. Автоматической
подстановки похожего имени нет, чтобы не применить изменения к другому герою.

## Действующий персонаж

TurnRequest.acting_character — точное имя персонажа из active_characters, который
совершает действие. TurnOrchestrator заполняет его по PlayerAction.character_id; предварительная
проверка Engine гарантирует, что такой персонаж есть в состоянии. Имя не из active_characters
вызывает ошибку валидации Pydantic при создании запроса: это ошибка вызывающей стороны,
а не ответа модели, поэтому попытка исправления не расходуется.

Промпт хода содержит блок «ДЕЙСТВУЮЩИЙ ПЕРСОНАЖ»: последствия самого действия относятся к нему,
изменения другим героям допустимы, только если narrative явно описывает, как их затрагивает
последствие. Это инструкция модели; validate_turn не запрещает state_updates для других героев,
потому что взрыв, лечение группы и т. п. законно затрагивают нескольких персонажей.
Пустая строка (по умолчанию) означает «не указан»: модель определяет персонажа по тексту
действия, как раньше.

## Выполнимость изменений состояния

validate_turn до передачи ответа в Engine проверяет то, из-за чего Engine отклонил бы
весь ход. Тогда модель получает ту же единственную попытку исправления, а не тратит ход:

- items_removed — только предметы из inventory этого персонажа в текущем запросе,
  с точным совпадением названия и не больше имеющегося количества. Изменения проверяются
  в том порядке, в котором integration превращает их в команды: внутри одной записи
  state_updates сначала items_added, затем items_removed, записи — по порядку.
  Поэтому предмет, добавленный ранее в этом же ходе, можно убрать. Описание ошибки
  содержит недостающие предметы и фактический инвентарь персонажа;
- new_location и новые items_added не могут быть пустыми или состоять из пробелов.
  Если героя никуда не перемещают, нужно вернуть new_location: null.

Для неизвестного character_name выводится только ошибка имени, без ошибки инвентаря.
Размер hp_change не проверяется: Engine сам ограничивает HP пределами от 0 до max_hp.
Engine остаётся окончательной проверкой. Например, он отклонит ход, если предмет добавлен
под уже существующим названием, но с другим item_id, а затем удалён в том же ходе.

## Ведение сцены и сюжетные зацепки

Промпт хода связывает ответ с намерением игрока: осмотр даёт наблюдения, разговор —
реакцию собеседника, взаимодействие — последствия заявленного действия. Повторный
осмотр без нового подхода и изменений обстановки должен давать краткий ответ без
повторной выдачи предметов, наград и полного пересказа комнаты. Новый подход может
открыть деталь, если она согласуется с доступным контекстом. Продвижение сюжета не
обязательно на каждом ходу: мастер не выбирает за игрока реплики, чувства и маршрут.

В dm_thoughts модель сохраняет 1–2 предложения с актуальной зацепкой, намерением
собеседника или незавершённым последствием. Рекомендуются конкретные имена и предметы,
чтобы заметки находились поиском по истории. Разрешённые зацепки и изменившиеся
намерения отмечаются явно; возможное отделяется от случившегося, раскрытое — от тайного.
Это краткие факты для продолжения, а не рассуждения модели или копия всего скрытого
сюжета. Формат остаётся обычной строкой, пустая строка допустима. Новых полей нет.
Существующий путь dm_thoughts → TurnOutcome.dm_notes → TurnHistoryEntry.dm_notes
сохраняется: в историю попадают только принятые ходы, а состояние применяет Engine.

При отсутствии нужных правил или результатов броска промпт запрещает придумывать
число на кубике, сложность, урон и ссылки на правила. Модель должна описать наблюдение
или незавершённую попытку без неподтверждённых изменений. Даже при наличии правил
она не должна выдавать намерение игрока за уже выполненное действие.

Это инструкции LLM, а не новый семантический валидатор. Существующие проверки JSON,
имён, письменности и инвентаря не гарантируют связность сюжета, согласованность повествования
с дельтой состояния или отсутствие раскрытия тайны. Число вызовов модели не увеличено;
все новые инструкции входят в прежний бюджет контекста, поэтому истории может поместиться меньше.

## Проверка качества сцен

ai_dm/scene_scenarios.py содержит шесть искусственно подготовленных входных ситуаций
и критерии ручной оценки: повторный осмотр, новый подход, давняя зацепка, разговор,
просьба раскрыть тайну и отсутствие правил. Эти тексты — тестовые данные, не результаты LLM.

Просмотреть сценарии без подключения к провайдеру:

~~~text
python -m ai_dm.evaluate_scenes
~~~

Отправить один выбранный сценарий подключённой модели из .env:

~~~text
python -m ai_dm.evaluate_scenes --live --case repeat_inspection
~~~

Другие значения --case: new_approach, old_clue, npc_dialogue, secret_request, missing_rules.
--live требует явного --case. Один запуск проверяет один ход, с существующими пределами
повторов и токенов. Это отдельные случаи, а не автоматически разыгрываемая кампания.
Команда не меняет состояние игры или БД и не обращается к справочнику монстров.

JSON-отчёт в stdout содержит исходную искусственную ситуацию, критерии, имя модели,
время, хеш файлов промптов перед вызовом и прошедший нормализацию и валидацию ответ.
Отчёт предназначен разработчику и содержит приватные поля тестовой сцены.
review_status остаётся pending: результат нужно оценить по каждому критерию вручную,
при необходимости повторив тот же случай. status=generated означает лишь получение
валидного ответа, а не прохождение проверки качества. При ожидаемой ошибке печатаются
тип ошибки и категория провайдера без его тела, программа завершается с кодом 1.
Фиктивный ответ вместо неудачного запроса не создаётся.

Автотесты используют подменённые ответы: они проверяют передачу контекста, бюджет,
сохранение заметок после принятия хода и работу команды оценки. Они не доказывают
качество реальной генерации. example_output.md не обновляется этими тестами.

## Демонстрация двух ходов

Запуск из корня проекта: python -m ai_dm.main. Нужны API-ключ и доступ к LLM;
при старте кампании также запрашиваются данные монстра из D&D API.

Демонстрация использует настоящие RulesService, TurnOrchestrator и Engine.
Встроенный русскоязычный текст правил — небольшой пример поиска, а не полная
книга D&D. DemoSession в ai_dm.main хранит состояние и историю только в памяти
процесса и показывает обязанности вызывающей стороны, не заменяя Backend.

Второй ход получает состояние, возвращённое Engine после первого принятого хода,
и его историю. При смене локации старое описание комнаты очищается; достоверное
описание новой комнаты должна предоставить вызывающая сторона. При отказе или
ошибке ход не добавляется в историю. Если первый ход не принят, второе действие
повторяет осмотр без ссылки на несуществующий результат предыдущего хода.
В демонстрации имя героя — «Элиас», а класс «Плут» хранится отдельно в concept
персонажа Engine. Приватные заметки не печатаются демонстрацией.

## Конфигурация

Импорт модуля не читает .env и не создаёт LLM-клиент. При первом обращении
к клиенту загружается .env без переопределения переменных окружения.

| Переменная | Значение по умолчанию |
| --- | --- |
| OPENAI_API_KEY | Обязательна при использовании стандартного клиента |
| OPENAI_BASE_URL | https://router.huggingface.co/v1 |
| MODEL_NAME | Qwen/Qwen3.8-27B |
| AI_DM_TIMEOUT_SECONDS | 60 |
| AI_DM_MAX_CONTEXT_CHARS | 24000 |
| AI_DM_MAX_OUTPUT_TOKENS | 1024 |
| AI_DM_MAX_RETRY_WAIT_SECONDS | 10 |

Таймаут должен быть положительным конечным числом; дробные секунды допустимы.
Он передаётся SDK как сетевой таймаут, а не общий дедлайн генерации.
Настройки клиента фиксируются при его создании; MODEL_NAME, AI_DM_MAX_CONTEXT_CHARS,
AI_DM_MAX_OUTPUT_TOKENS и AI_DM_MAX_RETRY_WAIT_SECONDS читаются для каждой операции
генерации. Для применения новых настроек клиента создайте новый экземпляр
AIDungeonMaster или перезапустите процесс.

SDK-повторы отключены (max_retries=0). Для переданного экземпляра OpenAI с включёнными
повторами используется копия настроек с max_retries=0; исходный клиент не изменяется.
Таймаут и закрытие переданного клиента контролирует вызывающая сторона.
Произвольный пользовательский клиент также должен отключать свои внутренние повторы:
модуль ограничивает число вызовов create, но не может контролировать его внутреннюю реализацию.

## Бюджет контекста и ответа

Оба новых лимита должны быть положительными целыми числами. Их можно задать в .env:

~~~dotenv
AI_DM_MAX_CONTEXT_CHARS=24000
AI_DM_MAX_OUTPUT_TOKENS=1024
~~~

Бюджет входа измеряется числом символов Unicode в сериализованном списке messages:
`len(json.dumps(messages, ensure_ascii=False, separators=(",", ":")))`.
Учитываются системная инструкция, JSON-схема, правила, скрытый сюжет, состояние,
действие, история, роли сообщений и экранирование. Это не число токенов и не размер
всего HTTP-запроса в байтах; параметры model, temperature и max_tokens не входят в бюджет.
Лимит не гарантирует соблюдения контекстного окна или TPM выбранного провайдера.

Перед каждым LLM-запросом модуль уменьшает оба блока истории по описанному выше
приоритету до попадания в бюджет. Остальной контекст не обрезается. Если он
не помещается даже без истории, возникает ContextBudgetError до отправки LLM-запроса.
Проверка действует и для старта кампании: тема, персонажи и полученные данные монстра
сохраняются целиком. Запрос к справочнику монстров может выполняться до этой проверки.

Для исправления учитываются также предыдущий ответ и описание ошибок. При необходимости
исключаются дополнительные найденные события, затем старые записи из последних ходов.
Поиск не запускается заново: повтор использует тот же отбор и может только уменьшить его.
Если места всё равно нет, запрос исправления
не отправляется; предыдущий ответ и описание ошибок не обрезаются. Ошибка бюджета не меняет
состояние Engine и сохранённую историю.

AI_DM_MAX_OUTPUT_TOKENS передаётся в Chat Completions как max_tokens и ограничивает
весь ответ, включая JSON и приватные поля, для провайдеров, поддерживающих этот параметр.
Системная инструкция просит один короткий абзац повествования и краткие заметки.
Количество предложений — пожелание модели, а не программная гарантия.
При finish_reason="length" ответ считается незавершённым, даже если JSON разбирается:
модель получает одну попытку вернуть более короткий полный ответ с тем же лимитом.
Повторное усечение завершает операцию с InvalidResponseError. Лимит автоматически не увеличивается.

## Проверка ответа и ошибки

Язык создаваемого игрового текста — русский. Системный промпт требует русских
названий кампании, локаций, новых предметов, описаний и приватных заметок, даже если
справочник монстров или действие игрока написаны по-английски. После разбора JSON
нормализуются визуально похожие латинские буквы внутри русских слов, например
`cклеп` → `склеп`, `двеpь` → `дверь`. Замена выполняется только в слове, где русских
букв больше, чем латинских, и все остальные символы — известные латинские двойники
(`ABCEHKMOPTXYaceopxy`). Целиком английские слова, равные доли двух алфавитов и
буквы без однозначной замены автоматически не исправляются.

Затем проверяются буквы: оставшиеся иностранные буквы и отсутствие текста
вызывают запрос исправления. Текст только из точного известного имени и пунктуации
(например, «Элиас.») тоже допустим. Пустые строки, одни числа или знаки препинания
без известной ссылки по-прежнему отклоняются; пустые dm_thoughts допускаются.
Это проверка письменности,
а не полноценный детектор языка: она не оценивает грамматику и смысл русских фраз.

Существующие имена персонажей, названия предметов и текущая локация разрешены в
повествовании хода в исходном написании. Точные ссылки защищены и от нормализации,
включая имена со смешанными алфавитами. Ссылка должна совпадать целиком: имя `Key`
не разрешает слово `Keys`. При генерации кампании известные имена и предметы разрешены
в описаниях и скрытом сюжете; название кампании и стартовая локация проверяются отдельно.
Поля ссылок на персонажей, удаляемые предметы, добавляемые
экземпляры уже известных предметов и текущую локацию не переводятся: это сохраняет
контракты Engine и integration. Новые названия локаций и предметов проверяются отдельно.
Нормализация применяется и к ответу на запрос исправления; она не расходует отдельный
вызов LLM. Исходный запрос и исходный объект ответа не меняются. Если модель снова
нарушает проверку, ответ не попадает в игру и состояние не меняется.

Для обоих методов применяется одна последовательность: получение текста,
удаление внешнего Markdown-блока при его наличии, проверка JSON по Pydantic-модели.
Отсутствующие варианты ответа и пустой content считаются ошибками формата.

После первой ошибки формата, языка или имени персонажа выполняется одна дополнительная генерация:
модель получает исходную схему, предыдущий текст (если он есть) и описание ошибок.
На одну операцию допускаются одна попытка исправления ответа и один повтор при временном
сбое провайдера. Общий предел — три вызова LLM. Два некорректных ответа завершают операцию
с InvalidResponseError; повтор при временном сбое не даёт дополнительной попытки исправления.

Исключения из ai_dm.errors:

- ConfigurationError — отсутствует ключ, некорректны настройки или не удалось загрузить/заполнить шаблон промпта.
- ContextBudgetError — обязательные сообщения не помещаются в бюджет даже без истории;
  поля required_chars и limit_chars содержат размеры, repair указывает на этап исправления.
- ProviderError — запрос к провайдеру завершился ошибкой; содержит безопасную категорию,
  HTTP-статус и рекомендованное ожидание, если они доступны.
- InvalidResponseError — ответ некорректен и после попытки исправления.

Все наследуют AIDMError. Исходные исключения сохраняются в __cause__ там, где они
есть. Сообщения об ошибках провайдера и окончательном отказе проверки не включают
ответ модели или скрытый сюжет; исходная причина может содержать приватные данные,
поэтому её не следует отправлять игрокам.

TurnOrchestrator уже оборачивает эти ошибки в integration.DungeonMasterError.
До валидного ответа DM команды в Engine не поступают. После ответа Engine продолжает
проверять игровые изменения самостоятельно; валидный JSON не гарантирует соблюдения
игровых правил.

Получение данных монстра использует прежний DnD5eClient: при недоступности данных
генерация использует «Базовый противник». Его таймаут не связан с AI_DM_TIMEOUT_SECONDS.

## Ошибки провайдера и повтор запросов

ProviderError остаётся наследником AIDMError и поддерживает прежний вызов
`ProviderError("сообщение")`. Ошибки, созданные модулем при сбое запроса, содержат:

| Поле | Значение |
| --- | --- |
| category | authentication, permission, quota, rate_limit, unavailable, invalid_request, timeout, connection или unknown |
| status_code | HTTP-статус или None при отсутствии ответа |
| retry_after | Допустимое значение ожидания от провайдера в секундах или None |
| retryable | Категория допускает повтор; это не означает, что повтор ещё доступен или уже выполнен |

HTTP 401 означает проблему с ключом, 403 — с доступом, 402 — с оплатой или квотой.
Коды insufficient_quota, billing_hard_limit_reached и insufficient_credits в поле
code или type тела ошибки HTTP 400/429 также определяются как исчерпанная квота.
Эти ошибки не повторяются. Остальные HTTP 429 считаются ограничением частоты;
свободный текст сообщения провайдера не используется для определения категории.
Другие провайдеры могут обозначать квоту иначе — список распознаваемых кодов ограничен.

Один автоматический повтор разрешён для HTTP 429 и серверных ошибок 500, 502, 503, 504.
Таймауты, ошибки соединения и остальные статусы завершают операцию сразу.
Повтор отправляет тот же запрос; новая попытка исправления JSON при этом не расходуется.
Лимит повторов действует на всю операцию, включая запрос исправления, и сбрасывается
при следующем вызове generate_campaign_start или process_turn.

Ожидание берётся из retry-after-ms либо Retry-After (секунды или HTTP-дата).
Отрицательные, бесконечные и некорректные значения игнорируются; дата в прошлом
означает нулевое ожидание. Если пригодного значения нет, задержка составляет одну секунду.
AI_DM_MAX_RETRY_WAIT_SECONDS задаёт максимально допустимое ожидание от 0 до 60 секунд,
по умолчанию 10. Ноль отключает автоматические повторы. Если провайдер требует ждать
дольше предела, операция завершается с ProviderError: задержка не сокращается ради повтора.
Ожидание синхронное; этот предел не является общим дедлайном сетевой операции.

В демонстрации ошибки провайдера отображаются по-русски как при старте кампании, так
и внутри DungeonMasterError при ходе. Ответ провайдера, ключ, адрес запроса и скрытый
сюжет не включаются в сообщение. Исходное исключение доступно разработчику через __cause__.
Повторы выполняются до передачи результата Engine: успешный ход применяется один раз,
а при окончательном отказе состояние и история остаются прежними.

## Проверки

Из корня проекта, используя интерпретатор окружения проекта:

~~~text
python -m unittest discover -s ai_dm/tests -t .
python -m unittest discover -s engine/tests -t .
python -m unittest discover -s rules_service/tests -t .
python -m unittest discover -s integration/tests -t .
~~~

Новые тесты не обращаются в сеть: ответы модели и D&D API подменены.
Проверки сетевых ошибок используют настоящий SDK с httpx.MockTransport.
Проверки совместимости используют настоящие RulesService, TurnOrchestrator и Engine.

Модулю нужны установленные openai, httpx, pydantic (версия 2) и python-dotenv.
В этом изменении общие файлы зависимостей проекта не редактируются.
